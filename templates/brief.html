THE ONE RULE THIS TEMPLATE EXISTS TO ENFORCE A fact and a reading are never allowed to look alike. CLAUDE.md puts it plainly -- "the numbers a function returns are facts, your reading of them is an opinion" -- and a page that renders an opinion inside a table cell has quietly promoted it to a measurement. So: facts live in .kpi tiles, .stat tiles, tables and charts, and every table names the SQL that produced it on the .n line above it -- `ads.fatigue.score`, not "score". If the source cannot be named, it does not belong in a table. readings live in a block-level element with a "Reading" eyebrow, the rule name in small type, and the citations that back it. NEVER in a table cell. proposals get a third label -- "Proposal -- not filed" -- and the command that would file them, so the reader can see for themselves that nothing has been filed. They are told apart by INDENT and a RULE-LINE, not by colour. base.html argues that case at :16-37 and it holds here for a reason beyond accessibility: colour would make a reading look like a severity, and the difference between an opinion and an alarm is the entire point. Readings carry a solid rule; proposals a dashed one. Shape, not hue. A NOTE ON WHAT IS NOT HERE Only the four chart helpers ui.py registers are used -- line_chart, bar_chart, sparkline and the money/num/pct/fmt formatters. charts.py also defines column_chart, which is not a Jinja global and is called from no template; using it here would render an exception, not a chart. ===================================================================== -#} {% block page_sub %}
